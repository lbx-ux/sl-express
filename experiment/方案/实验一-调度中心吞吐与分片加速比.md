# 压测方案 · 实验一：调度中心吞吐 + 分片广播加速比

> 目标：为简历「消息驱动 + 纯计算调度中心」「xxl-job 分片广播多节点并行调度、递归装车」提供量化数据，回答「分片广播到底带来什么收益」。
> 简历落点：「单次调度处理 5w+ 运单，双实例分片并行提速 X%，批量生成运输任务与司机作业单」。
> 结果文档：`experiment/测试结果/实验一.md`（待测）

## 一、被测链路（已核对源码）

```
压测脚本批量发运单消息
  → RabbitMQ 交换机 sl.exchange.topic.transportOrder.delayed (routingKey=JOIN_DISPATCH)
  → dispatch 服务 TransportOrderDispatchMQListener（合并运单）
      → Redis: LPUSH DISPATCH_LIST_{start}_{end} / SADD DISPATCH_SET_{start}_{end}
  → xxl-job 触发 DispatchJob.transportTask（分片广播）
      → 按 MOD(id, shardTotal)=shardIndex 拉取车辆计划（schedule_status=0、3h 内发车）
      → Redisson 公平锁(队列粒度) → 递归装车(载重/体积 95% 余量) → RPOP 队列
      → 发运输任务消息 → work 服务落库 sl_transport_task + sl_transport_order_task
```

**测量口径**：xxl-job 触发时刻 → Redis `DISPATCH_LIST_*` 全部队列清空 + `sl_transport_task` 行数稳定，这段时间内的运单处理速率（运单/秒）。

**对比设计**：

| 轮次 | dispatch 实例数 | 预期 |
|---|---|---|
| 基线 | 1 | 单实例处理 5w 运单总耗时 T1 |
| 对照 | 2（同 AppName，分片广播自动生效） | 车辆计划按 MOD(id,2) 分流，耗时 T2 |
| 加速比 | — | T1 / T2（理想 ~2，实测看锁竞争与 DB 瓶颈） |


**验证**：

```bash

docker exec redis redis-cli -a 123321 --no-auth-warning --scan --pattern "DISPATCH_LIST_*" | xargs -I{} sh -c 'echo -n "{}: "; docker exec redis redis-cli -a 123321 --no-auth-warning llen {}'
```

### Step 3：基线轮（单实例）

1. IDEA 启动 1 个 dispatch 实例 + work + base + oms
2. xxl-job 后台（xxl-job.sl-express.com，admin/123456）找到 `transportTask` → **执行一次**（执行器选择单实例）
3. 秒表计时：触发时刻 → Redis 队列全空 + `SELECT COUNT(*) FROM sl_work.sl_transport_task` 不再增长
4. 记录：T1、生成的运输任务数、司机作业单数

### Step 4：对照轮（双实例分片）

1. IDEA 再复制一个 DispatchApplication 启动配置启动第 2 实例（同 AppName `sl-express-ms-dispatch`，xxl-job 自动组成 2 分片；注意第二个实例要改 `server.port` 和 `xxl.job.executor.port`）

4. 计算：吞吐 = 50000 ÷ T；加速比 = T1 ÷ T2

## 四、面试防守问答

1. **为什么加速比不是理想的 2 倍？** 车辆计划按 MOD(id,2) 分流，若 id 分布偏斜则负载不均；且共享 Redis/MySQL，锁竞争（同队列两队列互斥）与 DB 写入是共享瓶颈——如实呈现加速比与瓶颈分析比吹「线性加速」专业。
2. **公平锁为什么必要？** 同一「起点-终点」队列可能被两个车辆计划竞争，公平锁保证先到先装、运单顺序不乱（LPUSH/RPOP 的先进先出语义依赖）。
3. **为什么运单要合并？** 相同「当前节点→下一节点」的运单装同一辆车，一次调度批量生成一个运输任务——合并是减少运输任务数、提升装车效率的前置。
4. **调度中心为什么不落库？** 「收消息 → 纯计算 → 发消息」，无状态可水平扩容；持久化交给 work 服务——这正是本实验能直接双实例扩容的前提。
5. **怎么保证运单不丢？** 消息确认（manual ack）+ 队列持久化；调度失败的运单仍在 Redis 队列中，下次调度继续消费——Redis List 既是缓冲也是待办。
