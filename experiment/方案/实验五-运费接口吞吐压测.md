## 一、实验设计

**被测对象**：`POST http://127.0.0.1:18094/carriages/compute`（carriage 服务，IDEA 本机启动，端口 18094）

**请求链路**：HTTP → Controller → 责任链（同城 → 省内 → 跨省 → 经济区，顺序逐节点匹配）→ MySQL 查 `sl_carriage` 模板表 → 首重/续重分段计算 → 返回

**两组对比**：

| # | 场景 | 压测方式 | 观测点 |
|---|---|---|---|
| 5a | 热缓存（正式轮） | 300 并发 / 300s | QPS 稳定水位 + TP99 |
| 5b | 冷启动对照 | 重启 carriage 后立即压 60s | 首波请求（模板首次回源 MySQL）的 RT 峰值与吞吐爬坡，量化冷启动代价 |

**无「责任链 vs if-else」对比组的理由**：两者均为纳秒级内存顺序判断，性能差异不可测；责任链的价值在扩展性（新增计费规则零侵入）而非性能，面试如实说明。

**请求体**（已按 `WaybillDTO` 字段核对）：

```json
{"senderCityId":545532,"receiverCityId":545533,"weight":1.5,"volume":1,"measureLong":20,"measureWidth":15,"measureHigh":10}
```

> 城市 id 须为 `sl_base` 库 `sl_area` 表真实存在的城市（同城/省内/跨省匹配依赖它）；同城用 545532→545533（成都两区，课程已验证可计费）。跨省组（545532→161792 上海）可选加压，观察不同模板命中路径的 RT 差异。

## 五、面试防守问答

1. **责任链 vs if-else 的真实收益？** 性能等价，收益在扩展性：新增计费规则 = 加一个 Handler + 调整链顺序，不动既有代码（开闭原则）。
2. **模板匹配为什么不加缓存？** 模板表仅 4~8 行，MySQL 主键查询 <1ms；Caffeine 收益在小表场景不明显——如实说明「表太小不值得缓存」比堆砌方案更专业。
3. **吞吐瓶颈在哪？** 每请求 1~2 次 DB 查询 + HTTP 序列化；可与实验二 Neo4j 接口（1713 QPS）横向对比，说明「每请求 DB 查询次数」对吞吐的影响。
4. **300 并发怎么定的？** 与 RateHub 压测口径一致，两个项目数据可横向对比（RateHub 缓存治理后 7k QPS vs 本接口每请求回源 DB）。
