## 3c. DB 故障注入（docker stop mysql，60s 停库窗口）

| 指标 | 数值 |
|---|---|
| 停库窗口 | 60s（脚本 ssh 自动 `docker stop` → 60s 后 `docker start`，全程输出留档） |
| **发号中断** | **零中断**——125s 观察窗口内每秒均有发号（无停滞、无失败） |
| 停库期间发号 | 275 个 |
| 全程发号判重 | 546 个 id 全部唯一 |
| 恢复自愈 | mysql 重启后 Leaf 无需重启即恢复号段加载（/cache 监控可见新号段就绪） |

**关键发现——step 动态扩容**：即使将 DB 中 step 手动改回 100 并重启 Leaf，Leaf 观测到持续取号流量后号段长度自动增长（100 → 800 → 1,600）。停库时刻双 buffer 已缓存约 2,400 个号，按实测 4.3 次/秒 ≈ 9.3 分钟缓冲，60s 停库远无法耗尽——零中断是双 buffer 机制的必然结果，且 step 自适应扩容进一步放大了容错窗口。结合 3a 压测后 step 曾扩至 640,000（双 buffer 共 128 万个号）的数据：**取号流量越大 → step 越大 → DB 故障时缓冲越久**，与官方「step = 高峰 QPS × 600，可撑 10-20 分钟」的设计逻辑吻合。

## 总结论

| 子实验 | 核心数据 |
|---|---|
| 3a 吞吐 | **9,808 QPS**、TP99 86ms、294w 请求零错误（2C 虚拟机 + HTTP 口径；官方 4C8G + RPC 为 5w QPS / TP999 1ms） |

## 简历句式（最终版）

> **分布式 ID**：基于美团 Leaf 号段模式（双 buffer 异步预加载）生成运单号，实测发号 9808 QPS、TP99 86ms、10w 并发取号零重复；注入 DB 宕机故障，停库 60s 期间发号零中断、恢复后服务自愈，并以实测验证号段长度（step）随业务流量动态扩容的容错机制。

## 面试防守问答

1. **TP99 86ms 与官方 1ms 差异？** 环境口径（HTTP + 虚拟机 NAT vs 内网 RPC）；号段逻辑本身纯内存，网络栈占大头。
2. **停库 60s 为何测不出边界？** step 自适应扩容使缓冲达 9 分钟以上，60s 窗口必然零中断；极端边界由 step 设计公式（高峰 QPS × 600）保障。
3. **为什么不用雪花/UUID？** SL+13 位长度约束、趋势递增对 InnoDB 聚簇索引友好、无时钟回拨问题。
4. **step 怎么定？** 官方建议高峰期发号 QPS × 600（约 10 分钟用量）；过小则频繁访 DB、过大则重启浪费号段——实验中实测了 step 随流量的自适应扩容行为。
