# 实验四测试结果：MongoDB 2dsphere 索引对比 —— 地理围栏查询性能

> 实验方案：`方案\实验四-MongoDB地理围栏索引对比.md`（2026-10-09 ~ 2026-10-10 执行）
> 结论：**10w 级多边形数据下，2dsphere 索引将查询 TP99 从 13s 降至 605ms（21.4 倍）、吞吐提升 100 倍；无索引在 150 并发下触发慢请求雪崩。**

## 实验背景

- 被测接口：`GET /scopes/location?type=2&longitude=&latitude=`（service-scope 服务，本机 18089；源码查询为 `polygon.intersects(point)` → `$geoIntersects`）
- 压测数据：**100,000 条**作业范围多边形（type=2、bid≥9200001、面状分布武汉/成都/北京城市圈 ±0.28 度、凸正多边形半径 0.005-0.015 度）+ 1000 个查询坐标 CSV
- 对比方式：同接口、同数据、同 150 并发档位，**有 2dsphere 索引（polygon）vs drop 后**各压一轮；无索引轮崩溃则降档补测

## 三、对比结论

| 指标 | 有 2dsphere 索引（150 并发） | 无索引 50 并发（稳定档） | 无索引 150 并发 |
|---|---|---|---|
| TP99 | **605 ms** | 12,975 ms | 雪崩（68.73% 超时） |
| 吞吐量 | **500.6 /sec** | 5.0 /sec | 5.3 /sec（崩溃） |
| 异常 % | 0.00%（15w 样本） | 0.00%（623 样本） | 68.73% |
| 并发承受力 | 150 并发稳定 | 50 并发 RT 已达 13s | 150 并发崩溃 |

**分析**：同为零错误稳定态，2dsphere 索引使 TP99 从 12,975ms 降至 605ms（**21.4 倍**）、吞吐提升 **100 倍**，并发承载能力高一个数量级。无索引轮「先正常后雪崩」的曲线直观展示了慢请求堆积的破坏力——下单高峰每单必查的自动分单链路，没有空间索引无法支撑。

## 五、面试防守问答

1. **为什么这么快？** 2dsphere 底层 B+Tree 组织 GeoJSON 空间键，查询先按空间范围裁剪候选集再做精确几何计算；无索引 = 10w 多边形逐个执行点面相交运算（CPU 密集）。
2. **每请求返回 ~40 个多边形、27KB，序列化不是瓶颈？** 是开销的一部分，但两组对比口径一致（同数据同接口），不影响索引结论；业务上快递员选取本就需要返回多个候选范围交调度中心均衡分配。
3. **MySQL 不行吗？** 8.0 InnoDB 支持 SPATIAL INDEX，但作业范围是结构不规则的多边形文档，MongoDB 文档模型天然贴合；与 Neo4j 实验同一逻辑——选型靠数据说话。
4. **为什么不用 Redis GEO？** Redis GEO 仅支持点（GEOADD），不支持多边形包含判断。

## 六、踩坑记录（setup 故事素材）

1. **自交多边形被拒**：v1 造数据采用「极角排序 + 随机半径」，实测 13.9% 自交（Edges cross），2dsphere 拒绝非法环 → 改为极角均分 + 固定半径的严格凸正多边形（数学保证简单环），10w 条 0 失败。
2. **服务端枚举校验**：v1 以 type=9 隔离压测数据，但服务端 `ServiceTypeEnum` 仅认 1/2，`codeOf(9)` 返回 null → NPE。**教训：设计压测参数前必须核对服务端的枚举与校验逻辑** → 改为 type=2 + bid 段隔离。
3. **响应体爆炸**：v1 多边形扎堆城市圈中心，单点最多命中 3.5w 个多边形（14MB 响应），150 并发直接打假死服务 → v3 改面状分布 + 缩小半径，单点命中 18~58 个（~27KB），150 并发稳定。
